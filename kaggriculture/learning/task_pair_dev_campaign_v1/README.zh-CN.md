# 历史开发比赛诊断

本目录用于比较三个已经存在的任务模型：`baseline`、`control`、`auxiliary`。它使用此前已经消费的两个种子角色、两个冻结对手和双方席位，共 24 场。相同作物模型贯穿所有比赛。这里是开发诊断：只有两个种子簇，不能作为独立测试、显著性证明或教师／模型晋级依据，也不改变之前开发筛查的结论。

运行必须先在公开仓库提交对应登记，之后才能读取本地历史种子和模型。`bootstrap` 由其标准库快照引导代码启动：先比对 Git 提交中的入口与身份校验字节，再验证登记、运行代码、官方规则和旧证据；只有这些检查通过且资源限制有效，才绑定本地历史身份。它拒绝复用已有尝试目录，不自动换种子或重试。登记、来源和完成状态是本机与仓库证据，不是第三方事前时间戳，也不能防止同一用户进程并发替换文件。

协调器使用官方引擎完成每场比赛，并复用现有保序重构及官方复演。每场均需检查 720 个状态、719 次动作、双方结束、进程退出、官方复演和现金闭合；每场接受记录与进程监督记录分别保存在本机。两组模型各有 8 条共同历史比较，共 16 条；比较记录和来源摘要也保存在本机。原始比赛、逐步观测、模型权重、真实种子和私有摘要不应发布。

`evidence.verify_and_project` 重新检查 24 场记录、16 条比较记录与它们的文件来源，再由 `projection.project` 从这些输入重算配对汇总，生成仅含白名单统计的公开账本。该检查不重新进行官方复演，也不能把本地记录变成外部独立证明。`projection` 区分被选中的任务、最后提交的单位请求、相关的官方原子执行与全场经济指标；移动请求并非已经种植。缺失标签和机会数不足均保留为未知。

入口会在加载 NumPy 前只为当前进程和子进程设置 `OPENBLAS_NUM_THREADS=1`、`OMP_NUM_THREADS=1`，不修改系统设置；这并非操作系统级原生线程上限。比赛进程使用既有 Windows Job 监督与采样，面板间的可用内存、磁盘和时限检查也是采样检查，不应解释为所有阶段均有硬内存上限。资源阈值和验收范围见对应的登记文件。

目前部分异常只留下固定失败信息、当前场次与已完成数量；如果子进程在写出单场收据之前退出，现有证据可能不能直接定位根因。届时应保留现场并调查，不能把退出码当作已知原因或自动重试。

这些模块的合成回归不读真实种子、模型、回放或训练数据，也不启动比赛；合成测试通过不能代替真实入口和完整比赛验收。复现时需要先核对登记对应提交、保持工作区干净，并由已认证的 `bootstrap` 快照引导执行准备、比赛和投影，不能直接运行未认证的私有合同。任何失败应保留现场，不能自行复用该次面板继续尝试。
