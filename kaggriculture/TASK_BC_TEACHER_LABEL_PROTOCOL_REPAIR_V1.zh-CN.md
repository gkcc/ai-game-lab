## 改动及实测

新 `protocol_checks(deadline, ledger)` 从第一个场景开始就把计数附着在调用者持有的账本。异常、最终断言或关闭失败不会只留下成功返回路径中的局部变量。计量仍复用冻结旧模块的读取器、前缀 JSON 解码器和关闭代码，没有修改它们的生产行为。

零余量场景通过一个受控的 64 KiB 缓冲边界，把小于该边界的压缩原文一次预取完；正余量场景限制底层单次读取最多 256 字节。覆盖不再靠 gzip 默认预读量恰好留下余量。这里的 raw、打开、读取字节全部来自内存合成对象，不是训练文件。

| 合成场景 | 实际读取与结果 |
| --- | --- |
| 零余量 | 19,098 压缩字节一次读取、一次完整哈希；drain 0 合法；解析 1 行 JSON |
| 正余量 | 前缀结束时读了 266 字节，随后 drain 18,832 字节；完整哈希一致；解析 1 行 JSON |
| 中途异常 | 第一次返回 2 字节，第二次读取抛出预定 OSError；读取开始 2 次、完成 1 次；没有完整哈希或成功解码 |

第三个场景在关闭之后，还针对同一份部分记录触发预定的完整性断言失败。原读取异常和最终 AssertionError 分开保留，调用者仍能看到已返回的 2 字节、未完成操作和未知量；没有追加第四次读取场景。该场景“通过”表示异常处理回归通过，底层读取本身仍是失败。

合计读取并散列 **38,198 个合成压缩字节**，返回 payload **18 字节**，完成 **2 次 JSON 解码**。两个正常前缀有 **2 项计划内缓冲未知量**；注入失败留下 **3 项失败未知量**。它们都保留为 null，不以零替代。所有 gzip、内存 raw 及附加 buffer／bridge 均关闭；关闭动作没有额外读取。
